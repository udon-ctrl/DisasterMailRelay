チームID

## 1. 背景と課題意識

現代社会ではスマートフォンが主要な通信手段となり、インターネットや基地局への依存度は極めて高い。

しかし、震災・水害・停電などの**広域災害時**にはこの前提が崩壊し、「**誰にも届かないSOS**」という事態が頻発する。

- 東日本大震災（2011）では一時的に**約8割の通信網が停止**
- 被災地では「メールを送っても相手に届かない」「SNSが更新できない」という声が多数
- 災害直後こそ**通信量が急増**し、ネットワークが輻輳して機能不全に陥る

その結果、**「無事です」の一言すら届けられない**という状況が生まれている。

---

## 2. 目的

「DisasterMailRelay」は、**電波がない環境でもスマートフォン同士が直接通信し、安否情報を中継して最終的にメールとして届ける**仕組みを構築する。

### 目標

- 携帯電波・Wi-Fiなしでも**短距離通信（BLE/Wi-Fi Direct）**でデータを中継
- 中継ノードを経て、最終的にオンライン端末が**自動的にメールを送信**
- 災害時でも最低限の通信（テキストメッセージ）を確保
- *「誰かが届けば、届く」**という希望を技術で支える

---

## 3. システム概要

### 3.1 概念図

```
[送信者A（オフライン）]
       ↓ BLE通信
[中継者B（オフライン）]
       ↓ Wi-Fi Direct
[中継者C（オンライン復帰）]
       ↓ SMTP
[宛先メールサーバ]
```

### 3.2 通信プロトコル：DisasterMailRelay/1.0

### データ構造（JSON形式）

<aside>

{
"protocol": "DisasterMailRelay/1.0",
"message_id": "UUID",
"sender": "hash_of_public_key",
"encrypted_body": "Base64",
"ttl_seconds": 3600,
"timestamp": 1730000000,
"signature": "RSA-SHA256"
}

</aside>

### 主要仕様

- **TTL（Time To Live）**：中継回数や時間制限を設定し、無限中継を防止
- **暗号化通信**：RSAで鍵交換、AESで本文暗号化
- **署名検証**：改ざん防止と送信者認証
- **重複除外（Duplicate Filter）**：`message_id`で同一メッセージを排除

## 6. 技術的アプローチ

### 6.1 通信方式

- **Bluetooth Low Energy (BLE) Advertising + Scan**
    
    → バックグラウンドでも低消費電力通信が可能
    
- **Wi-Fi Direct fallback**
    
    → 大容量データ転送や複数中継に対応
    

### 6.2 メッセージ配送アルゴリズム

- Opportunistic Forwarding（機会的転送）
- Gossip-style flooding（TTL制限付きフラッディング）
- 「最短経路」ではなく「最終到達率」を最大化

### 6.3 セキュリティ対策

- RSA2048による鍵交換
- AES256-GCMによる本文暗号化
- 署名付きハッシュで改ざん防止
- ローカルストレージ内は暗号化SQLite使用
